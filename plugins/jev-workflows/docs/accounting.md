# Accounting and request traceability

Local reservations, completed evaluations, and provider billing are different measurements.

- `budget.reservedAttempts` normally increments before network dispatch. It includes calls later cancelled, rejected, timed out, or otherwise unavailable. With configured limits, reservations serialize through the accounting lock and enforce those limits. When both limits are unlimited, recording is best effort: an advisory call proceeds if another live writer holds the lock, so `reservedAttempts` and `reservedPayloadBytes` can undercount contended calls and are not guaranteed-exact totals. `reservedPayloadBytes` counts serialized request bytes reserved locally, not tokens or money. The older `callsUsed` and `bytesUsed` fields remain compatibility aliases with the same reservation semantics.
- `evaluations.totals` summarizes selected retained local receipt evidence for the UTC day. Normal status reads the daily index; an explicit full audit scans a frozen filename inventory. It separates HTTP responses, successful HTTP statuses, validated evaluations, and unknown network outcomes. A malformed HTTP 200 response is not a validated evaluation. A timeout does not prove the provider did not receive or charge for a request.
- Both assessed and abstained evaluations can include token usage returned by TypeSafe. Abstention is an interpretation of the result, not evidence that no request occurred.
- `currentCredential` uses the current key's SHA-256 fingerprint. Receipts with a different valid fingerprint are counted in `otherCredential`, including when no current fingerprint is available. Receipts without a valid fingerprint stay in `unknownCredential`; every retained evaluation is therefore partitioned into exactly one of these three buckets.
- New receipts retain `transport.fetchInvoked`, request/response timestamps, HTTP status, validation state, and the provider's `x-typesafe-request-id` when present. Alternative observed `x-request-id` or `request-id` headers are supported. Missing IDs remain null. The local `receiptId` is distinct from the provider ID.
- A 401 response is classified as `authentication_failed`. A generic 403 is `request_forbidden`, because status alone does not prove a bad credential. For a 403 from the Codex network proxy, only the four documented `x-proxy-error` values are retained as `transport.networkPolicyError` and classified as `network_policy_blocked`; unrecognized header values and response bodies are discarded.
- Invalid responses carry an optional `transport.responseValidationFailure` category identifying the parser or validation stage. It contains only a fixed code, never a provider body, arbitrary field name, error message, or credential. Historical receipts without this category remain unexplained; this field is diagnostic evidence, not a billing result.
- Cached MCP results reuse the original local receipt and provider metadata, have `cached: true`, and do not make a new request or reservation. Previews and missing-key requests do not reserve.
- `providerBilledRequests` and `providerBilledTokens` remain null. No local counter is represented as provider billing. Request IDs and fingerprints aid investigation; they are not independent billing proof.

Receipts publish atomically without replacing an existing ID. Index updates are best-effort and can be skipped after a write interruption or when an index exceeds its update bound. A valid daily index is therefore not an authoritative full-day ledger.

`jev_status {}` reads the bounded current-day index and its referenced receipts. It never enumerates historical receipt files, falls back to a full scan or repairs an index. `scanMode` is `daily-index`; `inventoryFiles` and `unindexedReceiptFiles` are null because their census is unknown. `inventoryComplete` is false and `countsIncomplete` is true, with `full_inventory_not_scanned` plus any missing/corrupt-index or indexed-receipt diagnostics. Zero indexed receipts does not establish zero actual requests.

Request `jev_status {"fullReceiptScan": true}` only when you need a potentially slow full local audit. That mode enumerates retained receipt files, recovers omitted current-day evidence and reports index gaps. It can be cancelled; active file handles close and queued reads stop. Both MCP status modes are read-only and never repair or replace indexes or receipt files. Internal historical accounting callers retain their previous missing-index publication behavior.

`inventoryReadable` reports whether selected evidence could be read and parsed. An indexed result can be readable while its overall coverage is unknown. A full scan can report `inventoryComplete: true` when it encountered no known omissions; it still cannot detect receipts never published, removed before inventory or created after the frozen filename list. `scannedFiles` counts file-read attempts, including repeated reads during full-audit fallback. Provider billing remains unknown until reconciled with provider-side evidence.

Recorded decision outcomes are caller observations, not independent verification. The outcome schema requires the literal `callerReported: true`. An optional `providerRequestId` is accepted only when it exactly matches the referenced receipt; the persisted provider ID is read from that receipt rather than trusted from the caller. This verifies the local receipt linkage only. It does not verify that the reported outcome is true or that the provider billed the request.

## Reconciliation procedure

Compare the same account/key, workspace scope, UTC window, and dashboard filters. Retain the provider request ID, response UTC timestamp, HTTP status and usage from a controlled synthetic probe. Compare after the provider's stated dashboard delay, ideally against a provider export or support trace. Do not reset local counters, infer billing from status alone, or fabricate IDs for older receipts.

During development, a substantial gap was found between retained local response usage and the dashboard. The old adapter also discarded a provider request-ID header that a direct probe confirmed exists. This release fixes the adapter's missing traceability and misleading counter semantics. It does not claim a root cause for a provider-dashboard discrepancy without provider-side corroboration.
