# Paired coding-agent Jev study

Owner: root. Native goal created 2026-10-15 America/New_York. Source under study starts at plugin 0.5.1, repository 85f7832da59f955aced7e9fb0735d68384bbf21b. No product/global configuration changes are part of trial execution.

## Outcome and journeys

Measure the effect of the existing Jev integration within each coding host: Codex, Claude Code and QQ. A user asks for a code repair, the host edits a fresh project, then an independent hidden grader checks the resulting artifact. Both arms use identical task bytes, prompts, model, effort, tools, deadline and permissions. The treatment adds only Jev. Different vendors are not assumed to expose the same model; estimates are paired within each host and never pooled as a model ranking.

Reuse the existing paired-v1 fixtures, external grader logic, and paired statistical principles from the canonical plugin repository. The earlier four-task pilot is historical evidence, not a current-plugin baseline. DeepSWE's frozen 20-task study remains a separate real-repository protocol; this dependency-free diagnostic cohort must not be presented as its replication.

## Cohorts and frozen selection

Preflight one existing task once per arm and host, labelled plumbing only. Main development cohort uses the three existing portable tasks plus two newly authored multi-file repairs. Five repetitions per task and arm establish variation; repeated trials remain clustered by task, not independent samples. Balance on/off first order by task and repetition; use fresh sessions/workspaces/state each time. No outcome-based deletion or selective reruns. Failed attempts retain their scheduled slots. Run at most two model trials concurrently to limit host noise; this is an execution choice, not a Jev quota.

Reserve three newly authored tasks, with hidden graders frozen before provider results, for confirmation after choosing any fix. Do not inspect their solutions or grade outcomes while tuning. Confirmation uses five repetitions per arm if a timing claim will be made; single-run correctness diagnostics must be labelled as such and cannot establish a speedup. If the main cohort shows a ceiling, report it and do not claim general quality benefit. Preserve the existing real-repository study rather than replacing its denominator with easy tasks.

Scored configuration is GPT-6 Astra with high effort for both native Codex and QQ (QQ route `openai-codex/gpt-6-astra`), and exact `claude-opus-5-5[1m]` with high effort for Claude Code. Authenticated native catalogs confirmed the Codex/QQ intersection. The initial Codex CLI preflight rejected the unavailable GPT-6.1 Sol alias; its later ultra-effort attempt is plumbing evidence only. User defaults remain untouched. Claude and Codex vendor model families are distinct; only within-host on/off effects are causal targets.

Several plumbing attempts were retained after actual configuration, event cursor, timeout clock and receipt attribution failures. They are not scored task cohorts. Native trace evidence and unique transport receipts establish contact/delivery independently of counters. Packaging uses the canonical repository source for each host; an optional host-config JSON freezes explicit model/effort and executable/discovery overrides for reuse elsewhere.

## Task and adapter contracts

Corpus module exports development and confirmation task records: id, organic prompt, optional followups, candidate files, and an external grade(workspace) returning independent assertion results. Candidate-visible paths are neutral project slugs under a dedicated private runtime root, outside user source checkouts. Hidden checks, treatment labels and run plans are outside that workspace and never supplied to the agent. Baseline broken fixtures must fail meaningful checks; reference repairs must pass all checks. Grading runs after the model stops and does not feed hidden failures into a scored attempt. Reject or flag attempts to alter protected fixtures or read hidden runner paths.

Host adapters export async runTrial(options), where options includes workspace, prompt, followups, arm ('off'|'on'), model, effort, timeoutMs, outputDir, pluginRoot, nodePath and runId. They return exitCode, completion, requested/resolved model/effort, usage (inputTokens/cachedInputTokens/outputTokens/reasoningTokens; nullable), cost (reportedUsd/estimatedUsd/billedUsd; nullable with attribution), wallMs, session/run IDs, Jev receipt accounting and configuration/isolation evidence. Raw stdout/stderr/events are saved privately outside the project. A terminal text claim is separate from independently verified task completion.

Off means no Jev server/hook consultation or injected instruction. On must show real provider requests and evidence that any actionable advice reaches the host. A passive observer is recorded as observation, not as a causal decision intervention. QQ model routing is disabled in both arms to preserve the model; its native review mechanism and effects must be separately identified. Control contamination or wrong configuration invalidates the protocol. Provider failure, abstention, unused advice and treatment non-delivery after correct assignment remain in the intention-to-treat operational denominator; receipt coverage is a separate diagnostic, never a success-only filter.

## State, auth, privacy and recovery

Private append-only JSONL run records plus atomic per-trial receipts are the durable source. Freeze corpus, prompts, plugin snapshot, adapter versions, schedule and configuration hashes before scored runs. Never overwrite a started/completed trial; resume only unstarted rows. Model workspaces are disposable; patches, raw receipts, score records and source are retained. On interruption terminate only owned process groups, record partial result, and preserve originals. No production database migration or restore is needed. QQ may append isolated QA sessions through its existing server without restarting the user's server/TUI or modifying original sessions.

Reuse functioning auth through documented host interfaces. No credential export, account onboarding, API-key creation, security weakening, global plugin toggles, browser/CUA, external posting, cloud purchase or hosted Actions. Do not expose credential values to task commands, prompts or results. Environment settings and per-run Jev state must not alter user's product policy or artificial limits; no product quotas are introduced. Same filesystem/network permissions in both arms; ordinary safe disposable task edits are authorized.

## Metrics and analysis

Primary correctness is all-required-check artifact pass/fail, averaged over repetitions within each task and then equally over tasks. Assertion pass fraction is secondary. Missing artifacts are failures in the scheduled operational denominator and separately unknown in the code-quality sensitivity analysis. Completion requires terminal host success plus correct artifact; report host terminal success and false completion claims separately. Infrastructure errors, denied tools, provider failures, invalid outputs, timeouts and missing data remain explicit in scheduled denominators.

Measure monotonic end-to-end wall time including hooks, with startup/agent/grading components separately when available. Collect actual provider token usage and cached subsets; do not add cached tokens to input if already included. Record Jev attempts, responses, validated responses, abstentions, request IDs, latencies and nullable usage separately. Provider-reported estimated charges are not reconciled bills. Subscription hosts may report token usage without marginal dollars; billedUsd stays null. Never substitute API list prices as paid subscription cost. Cost comparison must disclose coverage.

Report paired correctness differences per host using equal task weights after averaging repetitions. Use deterministic task-cluster bootstrap intervals, with degenerate all-tie intervals explicitly not evidence of equivalence; exact discordant-pair tests, if reported, use only the preregistered first repetition per task. Report all-attempt wall time including failures and timeouts, and label any successful-only view. Report per-task medians/ranges, token deltas and cost coverage. Distinguish actual executed workload from denied/no-op runs. Keep all failures, provider caching and shared-host load evidence. No general speed/quality claim from an underpowered, ceiling or contaminated cohort.

## Repair rule and acceptance

Inspect observed treatment mechanisms and failures; fix concrete integration/data projection/feedback/accounting problems with meaningful regression coverage. Freeze a new plugin/adapter identity for any changed cohort. Do not rewrite the baseline or tune hidden confirmation cases. Use untouched confirmation tasks to estimate repaired-on versus off; this does not identify the repair effect versus old-on. A claimed repair-versus-old-on effect requires freezing and running an old-on confirmation arm before viewing outcomes. Preserve negative results, and recommend selective use or disabled ineffective features when justified. Do not change installed user defaults merely to improve a study result.

Acceptance: reusable runner and adapters validated on all three real hosts; preflight isolation and artifact grading proved; preregistered paired runs completed or concrete external dependencies recorded without fabricated results; correctness/completion/time/cost coverage report with raw evidence; demonstrated problems fixed and independently reviewed, then checked on fresh tasks; meaningful local verification and cleanup completed. No merge or official-store approval is implied.
